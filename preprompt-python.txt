1. OVERVIEW & PURPOSE
================================================================

This preprompt supports writing Sapio extensions in Python: primarily webhooks (CommonsWebhookHandler, rules, ELN handlers) and standalone scripts that use SapioUser and sapiopylib REST clients. Scope: scenarios covered by sapio://examples/python/invocations/* and sapio://examples/python/features/*. Assume the target Sapio system has a defined data model; obtain model details from the user's environment (not from this MCP server).

================================================================
2. WEBHOOKS VS STANDALONE SCRIPTS
================================================================

Webhook: A class extending CommonsWebhookHandler (or a focused rule base such as OnSaveRuleHandler / ElnRuleHandler where the example shows it) with def run(self, context: SapioWebhookContext) -> SapioWebhookResult:. Context provides user, experiment, entries, and record access appropriate to the invocation. Prioritize sapiopycommons (CallbackUtil, RecordHandler, ExperimentHandler, etc.) for dialogs, File Bridge, and context-driven record work—see sapio://docs/cursor-rules.

Standalone script: Construct SapioUser(url=..., api_token=...) pointing at the customer's /webservice/api base; use DataMgmtServer, DataRecord helpers, and paging types from sapiopylib as in the feature examples. Do not embed credentials in shared code.

3. SAPIOPYLIB VS SAPIOPYCOMMONS (LIBRARY SPLIT)
================================================================

Use the correct package for each type. When unsure, copy imports from the fetched python-examples resource—do not guess modules.

Concern                                          | Package            | Examples (see python-examples)
-------------------------------------------------|--------------------|------------------------------------------------------------------
REST client, user session, DataMgmtServer        | sapiopylib         | SapioUser, DataMgmtServer in feature examples
Webhook context and result types                 | sapiopylib         | from sapiopylib.rest.pojo.webhook.WebhookContext import SapioWebhookContext; from sapiopylib.rest.pojo.webhook.WebhookResult import SapioWebhookResult
PyRecordModel, record/ELN POJOs used in code     | sapiopylib         | sapiopylib.rest.utils.recordmodel.PyRecordModel; ELN pojo imports in invocations
Webhook handler base, CallbackUtil, rule bases, RecordHandler / ExperimentHandler | sapiopycommons | CommonsWebhookHandler, OnSaveRuleHandler, sapiopycommons.customreport.* where used
Shared webhook exceptions                        | sapiopycommons     | sapiopycommons.general.exceptions

Anti-pattern: Do not attribute SapioWebhookContext, SapioWebhookResult, or PyRecordModel to sapiopycommons—they are sapiopylib. Do not attribute CommonsWebhookHandler, CallbackUtil, or OnSaveRuleHandler to sapiopylib—they are sapiopycommons. Webhooks normally import from both libraries.

4. ELN & GLOBAL RECORDS (CONCEPTUAL)
================================================================

Sapio tracks experiments (ELN) and global data records (instances of configurable Data Types). ELN types such as ELNExperiment, ELNExperimentDetail, and ELNSampleDetail are fixed platform types used inside experiments; entries live in tabs and can reference global types, ELN detail types, charts, or text. Unless the user asks to define ELN types or field sets, assume work uses ordinary global records and/or experiment content as they describe. Users edit ELN-type fields in experiment context; global types can be edited in entries or in table/form views.

7. REST & LIBRARIES AT A GLANCE
================================================================

The Sapio Web Service is rooted under /webservice/api on the customer instance. Typical authentication: header X-APP-KEY (application GUID) plus one of Basic auth, X-API-TOKEN, or Bearer token; optional X-USER-GROUP. Many list endpoints are paginated—use next page criteria from responses when iterating. Prefer sapiopylib and sapiopycommons over raw HTTP: they encode correct types, paging helpers, and webhook patterns. Do not paste full OpenAPI/Redoc into solutions; for raw endpoint details use the customer's API documentation or installed library source. Deprecated REST paths called out in product docs should be avoided in favor of documented replacements.

8. PERFORMANCE & QUERIES
================================================================

Prefer batch creates/updates and custom reports for read-heavy or list workflows when the fetched example uses them (sapio://examples/python/features/custom-report-manager; auto-pager patterns in selection-list or report examples). Avoid N+1 patterns: do not loop with one server call per record when a batch operation or report exists. For pagination, use next page criteria (see section 7) and patterns in sapio://examples/python/features/data-record-manager or report examples as appropriate.

10. ELN EXPERIMENTS & ENTRIES (PERSIST ORDER, ENTRY TYPES)
================================================================

Persist order (REST / webhook): typically create or update records first so new record IDs exist, then apply experiment entry changes, then complete the save/commit sequence shown in sapio://examples/python/features/experiment-entry-manager and the relevant webhook example. Always follow the fetched Python example; do not substitute APIs from unrelated stacks. After structural changes (e.g. new entries), refresh entry or experiment state before the next update when the example or API requires it.

Entry kinds: form-style, attachment-style, table-style, and plugin-style entries behave differently. Do not assume "one displayed record" means a single API pattern. Use template or API metadata and runtime checks as described in sapio://docs/cursor-rules and sapio://examples/python/features/experiment-entry-manager.

13. WEBHOOK RESULTS AND UX
================================================================

SapioWebhookResult (sapiopylib): Use success/failure and display_text or notifications only as demonstrated in the fetched example; do not add constructor or keyword arguments not shown there. Cancellation: catch SapioUserCancelledException (sapiopycommons.general.exceptions) per sapio://docs/cursor-rules and return a clean SapioWebhookResult instead of propagating uncaught. Dialog timeouts: SapioDialogTimeoutException (sapiopycommons)—see sapio://examples/python/features/client-callback for full dialog patterns.

User-facing text: In common informational displays (display_text, notifications, dialog copy, user-visible logs), show human-readable user names, not raw user IDs, unless the user explicitly asks for IDs or the context is clearly technical/debugging. Resolve display/login name via the appropriate API when needed; if unclear, ask the user (see sapio://docs/cursor-rules).

14. CONVENTIONS, COMMON MISTAKES & OUTPUT
================================================================

Use type hints on variables and function signatures (see sapio://docs/cursor-rules). Prefer built-in generics: list, dict, not typing.List or typing.Dict. Only use sapiopylib, sapiopycommons, and the Python standard library unless the user explicitly requests another library. When unsure of a class, ask the user rather than inventing names. Unless the user asks for explanation, output the code they need; keep prose minimal.

Common mistakes: third-party libraries; typing.List / typing.Dict; inventing REST paths or request shapes; ignoring user cancellation; pasting large OpenAPI excerpts into answers. Correct approach: fetch the exact sapio://examples/python/... resource and sapio://docs/cursor-rules; use CommonsWebhookHandler with def run(self, context: SapioWebhookContext) -> SapioWebhookResult: and avoid obsolete handler names from outdated tutorials.

For additional WRONG vs CORRECT patterns, fetch sapio://docs/cursor-rules.
